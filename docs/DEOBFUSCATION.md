# VexView 2.7.3 — deobfuscation notes

Everything that was done to turn `vexview-2.7.3.jar` (MC 1.12.2, 168 classes, 800 KB) into the
readable tree in `src/main/java`, plus the traps that cost the most time.

Numbers first:

```
143  obfuscated classes          → 143 restored names (bijection from the jar's own FML cache)
678  per-call-site string crypts → all decrypted and inlined
1 006 renames                    → recorded in ../deobf-mapping.tsv
4 922 func_*/field_* references  → mapped to MCP names (stable_39)
383  methods                     → local slots split by type, stack map frames recomputed
168  classes                     → javac 1.8, 0 errors
```

---

## 1. What the obfuscator did

| Layer | Effect |
| --- | --- |
| Class renaming | everything under `x.x.*` with names drawn from `{i,I}`, e.g. `x/x/x/x/iiiiiIIiiI` |
| Member renaming | **all** methods and most fields collapsed onto the illegal identifier `pcdlk,pcdlona`, overloaded by descriptor |
| String encryption | every literal replaced by `Decryptor.pcdlk,pcdlona("…")`, key = *calling class name + calling method name* |
| Slot reuse | one JVM local slot reused for values of unrelated types (`ClientCustomPacketEvent` → `byte[]` …) |
| Stack juggling | `aload_0; dup_x1; dup; pop2` style sequences that leave `this` on the operand stack across statements |
| Debug info poisoning | every `LocalVariableTable` entry for a method shares one name, including slot 0 |
| Metadata damage | `InnerClasses` attributes left half-broken; JAR still carried stale `fml_cache_*.json` |

Two accidents made the reconstruction possible at all:

* `META-INF/fml_cache_annotation.json` and `fml_cache_class_versions.json` were generated by
  ForgeGradle **before** the obfuscation pass and shipped inside the jar. They list the 143 original
  class names, the original names of every annotated event handler, and each class's interfaces.
* The 143 obfuscated classes match those 143 names exactly — a bijection, not a guess.

## 2. String recovery

The decryptor is caller-keyed:

```java
static String d(String s) {
    StackTraceElement e = new RuntimeException().getStackTrace()[1];
    String key = e.getClassName() + e.getMethodName();   // ← caller!
    // xor-ish loop over `s` with `key`
}
```

Consequences, both of which dictated the whole pipeline:

1. Renaming anything before decryption destroys all strings (the key changes).
2. Re-implementing the algorithm is unnecessary and risky: the bytecode is right there.

So the tool (`tools/src/DecryptRunner.java`) extracts each decryptor into a minimal synthetic class
and builds **caller stubs that carry the original class and method names**, then invokes them. The
obfuscator's own key derivation resolves exactly as it did in production.

Locating the argument was the second problem. `ldc "cipher"; invokestatic d` is the obvious shape,
but the obfuscator interleaves unrelated pushes:

```text
ldc "&/7…"                 ← the real argument (category name)
aload configuration
invokevirtual Configuration.load()
ldc "close"                ← last LDC seen, but NOT the argument
invokestatic d             ← consumes the first one
```

A "remember the last LDC" heuristic gets 668 of 678 sites. The correct answer is a dataflow pass
with ASM's `SourceInterpreter` (`tools/src/FindSites.java`): ask the frame which instruction produced
the value that is *actually* popped by the call. 678 sites, zero failures.

19 Chinese literals decrypt to U+FFFD garbage — the original author compiled a GBK source as UTF-8,
so the damage predates the obfuscator. Reproducing the garbage faithfully keeps behaviour identical.

## 3. Class names

The FML cache gives the names; the mapping needs evidence. The tool uses four independent signals:

1. **Per-package class counts** — the obfuscated package tree is a 1:1 image of the original one
   (both are `{23, 20, 10, 8, 7, 6, 6, 5, 5, 5, 5, 4, 3, …}` multisets). Verified with a multiset
   comparison over the 30 packages.
2. **Inheritance chains** — e.g. the class that extends `AbstractClientPlayer` is `VexPlayerEntity`;
   the two that extend `EntityArrow` / `EntityMinecart` are `VexEntityGeter$1/$2`.
3. **Dispatch tables** — `ComponentFactory` maps `"image"/"text"/"gifimage"/"spiltimage"/"mcimage"`
   to concrete tags, `NetPacketManager` maps `"gamemenu"/"scoreboard"/…` to packet classes. These
   pin down 25+ names exactly.
4. **Recovered strings** — `textures/guide.png` + `guide.hud` in a class with a `Pre` handler and a
   key listener can only be `GuideListener`.

All 143 are resolved this way; the package map and the rename table are in `deobf-mapping.tsv`.

## 4. Member renaming

Because everything is called `pcdlk,pcdlona`, names must be *generated*, and naive generation breaks
polymorphism. The renamer (`tools/src/RemapTool.java` + `tools/genmap.py`) is inheritance-aware:

* a method that overrides an external member (Minecraft, Forge, JDK, LWJGL) keeps its name;
* every class in one override chain gets the **same** new name (the root declaration decides);
* bridge methods follow the method they bridge;
* `@SubscribeEvent` / `@Mod.EventHandler` methods are restored from the FML cache by descriptor;
* the rest become `m1…mN`, fields `f1…fN`, static fields `s1…sN`.

Java also forbids what the bytecode allows: two members with the same name and parameters but
different return types. Four such collisions existed (`VexButton.m4`, `VexSlot.m4`,
`VexGifImage.m1`, `AbstractElementCollection.m1/m2`); the subclass side was renamed and the call sites
updated, so no behaviour changes.

## 5. Slot splitting — the hard one

This is what makes decompiled obfuscated Java "compile but lie". A single local slot holds, say, the
method parameter early on and a `byte[]` later; every decompiler merges them into one variable and
either fails to compile or quietly produces wrong code.

The fix is a normalising pass (`tools/src/SplitSlots.java`): a typed interpreter over ASM's analysis
framework computes the exact type of every stored value, each (slot, type-run) gets its own slot,
debug tables are dropped and stack map frames are recomputed with a hierarchy built from the jars
(not from `Class.forName`, which is 100× slower). Classes whose rewrite cannot be re-analysed are
emitted unchanged, so the pass is safe by construction.

## 6. Rebuilding a compilable Minecraft SDK

Forge no longer publishes `1.12.2-14.23.5.2860-userdev.jar`, and ForgeGradle cannot proceed without
it. `tools/src/BuildMcpJar.java` rebuilds the compile SDK from what *is* still published:

1. merge vanilla client + server notch jars;
2. apply Forge's `binpatches.pack.lzma` (LZMA → Pack200 → javaxdelta), verifying every Adler-32;
3. remap notch → SRG with `joined.tsrg` (hierarchy-aware);
4. remap SRG → MCP with `mcp_stable` (stable_39);
5. fold in Forge's own 1 434 classes;
6. apply `forge_at.cfg` (`tools/src/ApplyAT.java`) so access transformers such as
   `GuiTextField.width` becoming public are honoured.

The result is `libs/minecraft-1.12.2-forge-mcp.jar`; 1 131 of 1 131 patched classes matched their
expected checksums, i.e. the input jars are the exact ones Forge patched.

## 7. Decompilation strategy

No single decompiler handles this bytecode:

| Tool | Strength here | Failure |
| --- | --- | --- |
| CFR 0.152 | recovers slot reuse by suffixing (`var1_1`), good on the stack juggling | cannot structure 10 classes |
| Vineflower 1.11.1 | clean output, handles those 10 | crashes on 14 others (`iterateClashingNames`) |

So: CFR primary, Vineflower for the files CFR cannot structure, then a small deterministic
post-pass (`tools/fixups.ps1`) and hand repair for what neither can express (`** GOTO lbl-1000`
blocks, dropped `else` branches, missing private methods).

Finally the differential test suite (see `VERIFICATION.md`) compared the rebuilt jar against the
original for real, which is how the remaining artefacts were found.

---

## 8. Lessons worth keeping

* Reuse the obfuscator's own decryptor; never re-derive its algorithm.
* A stale Forge metadata file can be worth more than any heuristic — check `META-INF/` first.
* "Compiles" is not "correct": only differential execution found the `else` and conjunction bugs.
* Every decompiler has a failure mode; run two and pick per file.
* Recompute stack frames with a jar-derived hierarchy, and validate; never trust a transform that
  cannot be re-analysed.
